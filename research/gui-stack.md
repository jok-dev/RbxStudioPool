# GUI stack for the tray icon and its windows

Research for [#3](https://github.com/jok-dev/RbxStudioPool/issues/3), in service of decision [#21](https://github.com/jok-dev/RbxStudioPool/issues/21): a tray icon (Windows notification area) / menu-bar icon (macOS) with a menu, a small **management window** listing the pool's Studios, and a **settings window** with Open Cloud API key instructions and a password-style entry box. Windows and macOS now; Linux addable later. Checked on 2026-11-06 against the versions current that day.

## Recommendation

**Slint (1.18+), as a separate tray process (`rsp tray`, or a separate `rsp-tray` binary) that talks to the daemon's local API like the CLI and MCP fronts do.** Keep **Tauri v2** as the runner-up. Its tray-app primitives are the most mature, but it brings a webview, HTML/JS and a config/IPC/permissions layer, which is a lot for two small windows. Linux would also need webkit2gtk. Rule out **eframe/egui** (the root window can't stay hidden, which is still an open bug) and **iced** (no tray support, and no release since 0.14 in Dec 2025).

Hedge: Slint's `SystemTrayIcon` is new (added in 1.17, June 2026, with fixes in 1.18 and in the unreleased 1.19). If it falls short, keep Slint for the windows and drive the tray with `tray-icon` + `muda` on Slint's winit event loop (see the egui row below for the event-loop rules).

## Process model: same process or a separate tray process

The process model matters more than the toolkit choice, and every candidate pushes the same way:

- **macOS main thread.** Every candidate's tray needs an AppKit event loop on the **main thread**, and the tray must be created there. tray-icon says so outright: "On macOS, an event loop must be running on the main thread so you also need to create the tray icon on the main thread" ([tray-icon docs](https://docs.rs/tray-icon/latest/tray_icon/)). On Windows the event loop must run on the thread that owns the tray (same source). In one process, `main()` would have to give the main thread to the GUI loop and run tokio on worker threads. That works, but then the daemon's lifetime depends on the GUI loop. A daemon started headless (from the CLI, over SSH, in CI, or by the Linux "core with no backend" job from [#17](https://github.com/jok-dev/RbxStudioPool/issues/17)) should not link or start a GUI at all.
- **Windows desktops.** The daemon already moves threads between desktops (`SetThreadDesktop` for the pool desktop, as in `spikes/python-pool/desktop.py`). A window belongs to the desktop of the thread that creates it, so keeping the tray UI in its own process keeps it on the user's desktop and away from that code.
- **Fits [#14](https://github.com/jok-dev/RbxStudioPool/issues/14).** The design is already one daemon with thin fronts over one local API. The tray then becomes a third front, and a crash in the GUI can't take the pool down.
- **Linking.** On Linux, Tauri links webkit2gtk and GTK, and tray-icon's default backend links GTK + libappindicator ([tray-icon README](https://github.com/tauri-apps/tray-icon)). If the GUI lives in the `rsp` binary, the CLI won't start on a box without those libraries. A separate binary, or at least a cargo feature, avoids that.

Who starts the tray process (the daemon spawning it when a GUI session exists, or a login item) is part of the open "autostart" question on the map.

If the tray must instead share the daemon's process, Tauri is the easiest fit: `tauri::async_runtime` is tokio, and `async_runtime::set` accepts an existing tokio handle ([docs](https://docs.rs/tauri/latest/tauri/async_runtime/index.html)). Slint would need `slint::invoke_from_event_loop` to get data from tokio tasks to the UI thread. That is also what a separate tray process would do with its HTTP client.

## Slint licensing, concretely

This repo is public, has no licence file, and its Cargo metadata says `license = "UNLICENSED"`. GPLv3 therefore doesn't fit unless the project chooses a GPL-compatible licence. That leaves the **Royalty-free License 2.0**, which covers proprietary desktop apps at no cost ([terms](https://slint.dev/terms-and-conditions), [pricing](https://slint.dev/pricing)), on these conditions:

- Attribution, either (a) the `AboutSlint` widget in an "About" screen or dialog reachable from the top-level menu (or on a splash screen), **or** (b) the Slint attribution badge on a public web page, with the download page suggested. Either one is cheap here: an "About" item in the tray menu, or the badge in the README / Releases page.
- No embedded-systems use, and no shipping Slint on its own or exposing Slint's APIs from the app. Neither applies to a desktop tray app.

It is a real obligation, but a small one. If the project later goes open source, GPLv3 becomes an option too, and the royalty-free licence still works.

## Why not eframe/egui, which the ticket listed first

tray-icon + muda are solid, and the same team ships them inside Tauri. The problem is eframe's model: one root window that is supposed to exist and be visible. A tray-first app has to fight that. The root can't start hidden ([#8459](https://github.com/emilk/egui/issues/8459), open), the `App::logic` split for doing work while hidden was proposed for this case ([#5113](https://github.com/emilk/egui/issues/5113)), and macOS has to share the main thread with tray-icon. Dropping eframe for raw `egui-winit` + a renderer would avoid these problems, but then we'd be writing our own application shell, which Slint and Tauri already provide.

## Open items for the UI prototype ticket

- Check Slint `SystemTrayIcon` on macOS 26 and Windows 11: left-click opens the management window (on macOS, `clicked` doesn't fire when a menu is attached, so either the menu holds "Open…" or the menu is left off), the menu updates live, and `Accessory` policy hides the Dock icon for a bare (non-`.app`) binary.
- Decide whether the shipped macOS artefact is a bare binary or a `.app` (this affects `LSUIElement`). It ties into the release-pipeline research ([#19](https://github.com/jok-dev/RbxStudioPool/issues/19)).
- Custom-rendered password fields (Slint, egui, iced) don't call `EnableSecureEventInput` on macOS; only WKWebView does. The key will usually be pasted, so this is a minor gap. Note it, or wrap the settings field's focus in a platform-module call if wanted.
- Measure release binary size for a Slint tray + two windows. No first-party figure was found, and nothing was built for this research.
